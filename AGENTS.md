# oxDNA repository instructions

oxDNA implements molecular simulation algorithms for coarse-grained modeling primarily of nucleic acid biophysics and nucleic acid nanotechnology structures, as well as additional soft matter models. The median structure run with this model is ~15k particles, but structures up to millions of particles must also be supported.

## Repository layout

This repo holds three related projects:
- **oxDNA** (C++/CUDA simulation engine) — `src/`, built with CMake into `build/bin/` (`oxDNA`, `DNAnalysis`, `confGenerator`).
- **oxpy** — pybind11 Python bindings to the engine, in `src/oxpy/` (built when `-DPython=ON`). It has its own `src/oxpy/AGENTS.md`; read that when working there.
- **oxDNA_analysis_tools (`oat`)** — Python analysis package in `analysis/`. It has its own `analysis/AGENTS.md`; read that when working there.

`contrib/` holds user-contributed interactions/observables/moves (each subfolder with a `CMakeLists.txt` is auto-added and builds plugin shared libraries). `legacy/` is code only compiled with `-DLEGACY_CODE=ON`. User docs (Sphinx/MyST) live in `docs/source/`.

## Build

```bash
mkdir -p build && cd build
cmake ..                 # CPU only; additional options -DCUDA=ON, -DPython=ON, -DG=ON (opt+debug symbols), -DDebug=ON, -DZSTD_ENABLED=ON
make -j8
make install             # needed with -DPython=ON to install oxpy (+ oat); CI uses -DPython=1 -DOxpySystemInstall=1
```
`CMakePresets.json` has presets (`g_only`, `g_python`, `g_cuda`, `g_cuda_python`) that all configure into `build/`. Precision defaults to double on CPU (`DOUBLE=ON`) and mixed/float on CUDA (`CUDA_DOUBLE=OFF`). On macOS keep `SIGNAL=OFF`.

## Conventions

The code must compile as C++14 (the default) and as C++17 (which CMake selects for CUDA 13+ builds). Code uses tabs for indentation.
Minimum Python version is 3.11 but oxpy and oat must also work with the latest Python release.
Maintain good software hygiene. File parsing and shared functions go in src/Utilities/ not individual files. Files should implement what their name suggests and nothing more.
Look for existing implementations of functions before implementing them.
The code must always be backwards-compatible (except in very extreme cases). A new feature must not change how a structure run with a specific parameter set in the previous version would behave. All breaking changes must be documented in `breaking_changes.md`. Bug fixes may change results, but this must be stated explicitly in the PR description and in `CHANGELOG`, together with how the old behaviour was wrong.
Keep dependencies minimal. Any external C++ libraries beyond the standard library must be under optional flags and either packaged with oxDNA (like Pybind11) or with automatic build instructions in the CmakeLists.txt (like Zstd).
All Python dependencies must be installable with a basic pip/conda installation command.
The code is expected to compile on Linux and MacOS using gcc or clang. Windows is not supported at this time.
Do not commit files generated by examples/tests.
Do not change any of the *model.h files. If you are developing a new force field, make a new model file.
Do not bump the `RELEASE` macro in `src/defs.h` or create git tags: releases are done by the maintainers.

### Design

- Do not copy an existing interaction to create a variant of it. Reuse it through inheritance, templates or composition (e.g. a class that owns the new model and delegates the nucleotide-nucleotide pairs to the unchanged DNA2/RNA2/NA interaction). Copies drift apart and their bugs have to be fixed many times: `DNANMInteraction` and `RNANMInteraction` are near-copies of each other for this reason.
- Structures can have millions of particles: avoid memory or time that scales with the square of the number of particles (e.g. dense N x N parameter arrays), on both the CPU and the GPU.
- Validate input files and fail with an `oxDNAException` that names the file and the line. Never let a parser silently skip, truncate or misread data (e.g. stream-based `>>` parsing that loses track of the columns when a line has an unexpected number of fields).
- New features that read topologies must support both the old and the new topology formats (see below), or give a clear error if they need information that only the new format provides.

### Strand direction and topology formats

oxDNA's historical convention lists nucleotides in the 3' -> 5' direction, the opposite of most other nucleic acid software. The two topology formats list them in opposite directions:
- classic (old-style) topologies are written 3' -> 5': each line is `strand base n3 n5`, and the first nucleotide of a strand is its 3' end;
- new-style topologies (header ending in `5->3`) give one sequence per strand, written 5' -> 3'.

The particle index follows the order of the topology (and of the configuration file, whose lines match the topology), so it runs 3' -> 5' along a strand with classic topologies and 5' -> 3' with new-style ones. Code must therefore never infer the direction of a strand from particle indices: use `p->n3` (the neighbour towards the 3' end) and `p->n5`. Bonded nucleotide pairs are evaluated as `(p, p->n3)` (see `DNAInteraction::_check_bonded_neighbour`, which swaps the particles if needed). Tools that convert between the formats must reverse the order of both the topology and the configuration, and sequences imported from other software are usually 5' -> 3'. For proteins (ANM topologies), sequences are N -> C terminus and, with the ANMT models, `n3` is the N-side (previous) and `n5` the C-side (next) amino acid.

### Units

Simulation units: 1 length unit = 8.518 Angstrom; the energy unit is such that kT = T(K) / 3000 (so 0.1 at 300 K); the mass of a nucleotide is 1.

## Tests

The C++ engine is tested by running short simulations and comparing outputs (`test/TestSuite.py`):
```bash
cd build
make test_run        # smoke test: every folder runs (CI on every push)
make test_quick      # compare observables against reference values (CI on PRs)
# single folder: run from test/ with a list file containing just that folder
cd ../test && echo "DNA/SSDNA15/MD" > /tmp/one.txt && ./TestSuite.py /tmp/one.txt ../build/bin/oxDNA quick
```
Each test folder (listed in `test/test_folder_list.txt`) has `LEVEL_input` and `LEVEL_compare` files; reference values are regenerated with `test/PrepareCompareFiles.py`. Compare-file syntax and available test classes are in `test/howto.md`. The simulation tests take quite a while, only run when necessary (preparing for a merge or testing a significant change) and inform the user that the test will take time. Preferably run in background.

Python side (after `make install` with Python on): `pytest analysis/tests/test_cli/` and `python examples/OXPY/run.py` as an oxpy smoke test.

### Verifying physics changes

Passing the test suite is not enough to show that a change to an interaction, a force or an integrator is correct:
- **Refactors must give identical output.** The default build uses `-ffast-math`, so moving arithmetic around changes the last digits even when the maths is unchanged. To check a refactor, build both the parent commit and the new one with strict floating point (e.g. with `-DCMAKE_CXX_COMPILER_LAUNCHER=<script>` where the script runs `exec "$@" -fno-fast-math -ffp-contract=off`, so that the flags come after the project's `-ffast-math`) and compare `energy.dat` and `last_conf.dat` byte by byte on the systems the change affects.
- **Reference values must be validated independently.** The `quick_compare` files store numbers and the test suite only checks that they don't change, so a value recorded from buggy code makes the bug permanent. Derive the reference of a new test from an independent calculation (e.g. a numpy implementation of the potential, an equivalent model or the original implementation) and say in the PR how it was obtained.
- **New forces and interactions need an energy-conservation check**: run MD with `thermostat = no` and check that the total energy does not drift. This catches forces and torques that are not the derivatives of the energy, which a step-0 energy test cannot see. If external forces are present, include their energy (note that the `force_energy` of a mutual trap counts each pair twice, so the conserved quantity is E + ext/2).
- **CUDA code needs a CPU vs GPU force comparison**: copy the GPU forces and torques back to the host after `compute_forces` and compare them, particle by particle, with the output of the CPU `force_and_torque` observable on the same configuration. Also compare the average energies of CPU and GPU runs. CI does not run CUDA: the PR must say on which GPU and in which precision (`float`, `mixed`, `double`) the code was tested, or that it was not.

## Documentation

The user documentation is written in Markdown (MyST) with Sphinx directives, in `docs/source/`, and is published at https://lorenzo-rovigatti.github.io/oxDNA/ by the `build-docs` GitHub workflow (on releases). Update it in the same pull request as the code it describes:
- input-file options of the engine and of the interactions: `docs/source/input.md`;
- external forces: `docs/source/forces.md`; observables: `docs/source/observables.md`;
- configuration and topology formats: `docs/source/configurations.md`;
- oxpy: `docs/source/oxpy/` (see `src/oxpy/AGENTS.md`); oat: `docs/source/oat/` (see `analysis/AGENTS.md`).
New pages must be added to a `toctree` (e.g. in `docs/source/index.md`), or Sphinx will not include them.

The oxpy and oat pages are generated from the docstrings of the installed packages (`autoclass`/`autofunction`) and from the oat argument parsers (`sphinx-argparse`), so oxpy and oat must be built and installed in the environment used to build the docs. To build them locally:

```bash
mkdir -p build && cd build && cmake .. -DPython=ON && make -j8 && make install && cd ..   # oxpy (and oat)
python -m pip install -r docs/docs_requirements.txt
cd docs && make html                          # output in docs/build/html/index.html
```

Check that the pages you changed render correctly and that the build does not print new warnings (broken references, missing modules, malformed directives). Do not commit `docs/build/`.

## Engine architecture

Execution flow: `oxDNA.cpp` parses the input file (`Utilities/parse_input/`) → `Managers/SimManager` → `Backends/BackendFactory` builds a `SimBackend` subclass chosen by `backend`/`sim_type` (MD, MC, VMMC, FFS_MD, PT_VMMC, min, FIRE; CUDA variants in `src/CUDA/Backends/`). `DNAnalysis` uses `AnalysisManager`/`AnalysisBackend` to re-run observables over an existing trajectory; `confGenerator` uses `GeneratorManager`.

Pluggable components are all created by string-keyed factories reading the input file, and each class implements `get_settings(input_file&)` / `init(...)` reading its own keys via `getInput*` helpers:
- **Interactions** (`src/Interactions/`, `InteractionFactory.cpp`): the force field (`interaction_type = DNA2`, `RNA2`, `DNA3`, `LJ`, `patchy`, …). Base class `BaseInteraction`. CUDA versions live in `src/CUDA/Interactions/` and are selected in `CUDA/Interactions/CUDAInteractionFactory`; some CPU interactions have `_nomesh` variants used with CUDA.
- **External forces** (`src/Forces/`, `ForceFactory.cpp`): `BaseForce` subclasses, keyed by the `type` string in the external-forces file (old `{}` format or JSON). Adding one requires: the class, an `else if` in `ForceFactory::add_force`, the `.cpp` in `src/CMakeLists.txt`, docs in `docs/source/forces.md`, and — if it should work on GPU — a CUDA struct/kernel in `src/CUDA/Forces/forces_defs.cuh` plus the `typeid` dispatch in `src/CUDA/Backends/MD_CUDABackend.cu` (unsupported types throw there).
- **Observables** (`src/Observables/`, `ObservableFactory.cpp`): `BaseObservable` subclasses printed through `ObservableOutput` (`data_output_N` blocks in the input file).
- **MC moves** (`src/Backends/MCMoves/`), **boxes** (`src/Boxes/`), **neighbour lists** (`src/Lists/`), **thermostats** (`src/Backends/Thermostats/`, CUDA in `src/CUDA/Thermostats/`).
- **Plugins**: `PluginManagement/PluginManager` loads observables/interactions/moves from shared libraries via `extern "C"` `make_<Name>()` entry points — the route `contrib/` uses.

Core types: `number` (double/float per build) and `LR_vector`/`LR_matrix` from `src/defs.h` and `Utilities/`; particles in `src/Particles/` (`BaseParticle`, `DNANucleotide`, …); shared simulation state (particles, box, interaction, forces, time) is accessed through the `CONFIG_INFO` singleton (`Utilities/ConfigInfo.h`). Errors are reported by throwing `oxDNAException`; logging via `OX_LOG`/`OX_DEBUG`.

### CUDA

Things that are not obvious from the code:
- The CUDA interaction is a different object from the CPU interaction whose `read_topology` is called by the backend. Anything the CUDA code needs from the topology or from other input files must be read again in its `cuda_init` (or taken from `CONFIG_INFO`).
- The GPU computes forces and torques only; the energies printed in `energy.dat` are computed by the CPU interaction on the GPU configurations. A bug in the GPU forces therefore does not show up in a step-0 energy test.
- `use_edge = true` (pair-based kernels) is not available in double precision, so a new interaction must also provide the neighbour-matrix version of its kernel.
- With `CUDA_sort_every > 0` the particles are reordered on the GPU, so the array index is not the topology index: use `get_particle_index()` to look up per-particle data stored by topology index, or refuse to run with sorting.
- The fourth component of `c_number4` is a `float` even in double precision (it stores the particle type and index, or an energy), and `_module()` uses `sqrtf`: use `sqrt(CUDA_DOT(r, r))` when double precision matters.
- `__constant__` memory belongs to the `.cu` file that defines it: a header that declares constants (e.g. `CUDA_DNA.cuh`) gives every `.cu` file that includes it its own copy, which that file has to fill with `cudaMemcpyToSymbol`. To reuse device code from another interaction, include its header (in a namespace if names clash) and copy its constants from your own `.cu` file.
- On case-insensitive file systems (macOS) check that new files under `src/CUDA/` are actually added to the commit (`git status`), since ignore rules written for a lowercase `cuda/` directory can match them.

oxpy bindings are in `src/oxpy/bindings_includes/` (one header per exposed class) registered in `bindings.cpp`; new public C++ API meant for Python must be exposed there (see `src/oxpy/AGENTS.md`). The Python package version comes from git tags via setuptools_scm (`pyproject.toml`).

## Releases and breaking changes

- The `pre-commit` script (link into `.git/hooks/`) enforces that `#define RELEASE` in `src/defs.h` matches `git describe --tags`, and rejects whitespace errors.
- External libraries are in `src/extern/`: nlohmann JSON, TinyExpr++, fast_double_parser, zstdpp.
- `CHANGELOG` lists user-facing changes per release; `breaking_changes.md` documents past C++ API changes (e.g. `number` is a compile-time float/double, CUDA uses `c_number`/`c_number4`, plugins need a single `make_<Name>` entry point).

## Pull requests

- One topic per pull request, branched from the current `master`. Do not mix unrelated features or fixes, and do not base a PR on another unmerged branch unless the dependency is stated.
- Update the documentation in the same PR (see [Documentation](#documentation)) and check that it builds. Add user-facing changes to `CHANGELOG`.
- Add tests for new features (a folder in `test/` listed in `test/test_folder_list.txt` for the engine, `analysis/tests/` for oat), with reference values validated as described in [Verifying physics changes](#verifying-physics-changes).
- In the description, state what was tested (CPU/GPU, precision, simulation types, test suite level) and, explicitly, what was not (e.g. MC/VMMC, CUDA, double precision, old-style topologies).
